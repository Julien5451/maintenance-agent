# 3 分钟演示脚本

所有业务数据均为模拟数据。当前新镜像已通过真实探针及三条 HTTP 场景。演示前保持既有 Windows 代理和 WSL 中的 `scripts/runtime_proxy.py --serve` 运行，按 README 使用 `compose.runtime-proxy.yaml` 启动；打开 [界面](http://localhost:8501) 和 [API 文档](http://localhost:8000/docs)。先核验 `/health`，并查看本轮容器真实探针；健康检查本身不会调用模型。

1. **0:00–0:20，说明分工。** 单 Agent 理解故障类别，graph 保存用户原文依据、核实状态和合法动作，规则决定优先级与班组。人工批准后才建单，数据全部模拟。
2. **0:20–0:55，设备消歧。** 输入 `数控车床机械轴承异响，未停机。`，看到两台台账候选。补充 `是 A车间1号工位 的那台。`，展开 `automatic_tool` 记录，说明程序重查台账、没有隐藏模型请求；草案应为 EQ-001、P2、T-MECH。
3. **0:55–1:20，人工确认。** 批准前查询列表证明当前任务无工单；确认后展示编号。通过 API 用同一 draft_id 重复确认，仍只有同一工单。
4. **1:20–2:00，补充与取消。** 输入 `EQ-004 机械轴承振动明显增大。`，只追问停机；补充 `已经停机。` 后说明原设备核实保留、规则重新校验，草案为 P1/T-MECH。取消后该任务无工单。备选在完整报修后附越权优先级/班组指令，展示仍按规则且必须批准。
5. **2:00–2:30，持久化。** 可事先预建并明确标注一条待批准模拟任务，保存 task_id/draft_id。执行 `docker compose restart api`，侧栏恢复同一任务、版本不变；此命令保留既有容器的代理环境和数据卷。
6. **2:30–3:00，证据。** 原12：6/12→12/12，请求37→33、拒绝17→0、耗尽3→0；新表述4/4。114测试、容器真实探针及HTTP三场景分开报告。明确端到端耗时52.827→63.660秒并未改善，历史失败均保留，不作普适正确性保证。

## 演示备用 API 操作

FastAPI 文档在 <http://localhost:8000/docs>。创建任务用 `POST /tasks`，请求体如 `{"text":"EQ-001 机械异响，已经停机。"}`。待确认后使用 `POST /tasks/{task_id}/responses`，请求体为 `{"action":"confirm","draft_id":"服务端返回的 draft_id"}`。重复该请求应返回同一工单，且 `GET /work-orders` 中仅新增一条记录。

确认只携带草案版本，不能通过 API 提交修改后的优先级或班组。取消用 `{"action":"cancel"}`，补充信息用 `{"action":"provide_info","text":"已经停机"}`。

## 演示检查

- 后端 `/health` 可访问，Streamlit 侧栏“检查后端”返回可读结果。
- 当前机器需保持代理及项目中继，内部 api/ui 请求不走代理；代码/环境改变后按 README 带 runtime override 重建。
- 设备 ID、示例输入与冻结用例保持一致。
- 真实模型报告必须来自真实 API；未执行时明确标注阻塞原因。
- 重启只重启服务，不删除 Docker 持久化卷；不要执行 `docker compose down -v`。

## B. 实际实现、职责分工与岗位对应

### 技术栈与实际版本

直接及间接 Python 依赖以 `uv.lock` 为准，`pyproject.toml` 限定 Python `>=3.12,<3.13`。已有环境报告记录 WSL Python **3.12.14**、容器 Python **3.12.16**；Docker Engine **29.1.3**、Compose **2.40.3** 是已验证环境版本。

六轮是 `tools` 节点的累计轮数；非法混合批次也占一轮，且其中每个 call 都保留拒绝记录和对应 `ToolMessage`。`model_calls` 另计实际模型请求尝试。确定性前置核实记录为 `automatic_tool`，不增加模型调用数或六轮计数，不能把它们隐去后将调用下降全部解释为模型能力改善。

HTTP接口包括 `POST /tasks`、`GET /tasks/{task_id}`、`POST /tasks/{task_id}/responses`（provide_info/confirm/cancel）、`GET /work-orders`、`GET /work-orders/{order_id}` 和 `GET /health`。任务返回状态、当前草案、规则依据、轮次、模型调用数及事件；健康检查不调用模型验证凭证。

### 本地代理中继与启动依赖

当前机器的原有代理实际由 **Windows 的 verge-mihomo 在回环地址监听**。WSL 能连到它，桥接容器不能把自己的127.0.0.1当作该代理。`scripts/runtime_proxy.py` 只读取并验证已有的、无凭证的回环 HTTP 代理，将项目 Docker bridge 网关上的18081端口中继至原代理；只允许本项目子网，不修改全局网络/防火墙、不关闭 TLS 校验、不记录流量。它是本机环境适配，不是通用生产代理服务。

`compose.runtime-proxy.yaml` 为 API 注入项目别名代理及动态网关；API/UI 的 `NO_PROXY` 覆盖内部服务，UI 对本地 API 还使用 `trust_env=False`。必须保持 Windows 原代理和 WSL 中继会话可用；网关变化后重新 `--inspect`。本机动态拓扑和实时计数文件不纳入 Git。构建代理模板 `compose.build-proxy.yaml` 与运行时代理配置用途不同，构建成功不代表容器运行时模型链路可用。

复现入口是 `README.md`、`reports/network_fix.md` 与 `docs/demo.md`：WSL 下 `uv sync --frozen`，配置本机 `.env`，分别启动 Uvicorn / Streamlit；Docker 在直连环境用基础 Compose，当前机器需 inspect、保持 relay，再使用基础文件加 runtime override。卷保存数据库，不能用 `down -v` 清除演示状态。本文引用的是已有验证结果，本轮没有重新验证代理或模型当前在线状态。

## C. 适合面试讲解的四项问题与修复

这些是通用代码与流程修复，具体用例只是观察结果，不按用例编号或整句报修文本特殊处理；没有修改模型权重或做模型训练。

### 1. 补充信息后设备核实被无差别清空

- **问题**：只补充停机或位置后，模型反复请求尚不合法的规则查询，无法在六轮内完成受理。
- **定位证据**：原始基线 `reports/real_eval/20261030T121646787416Z.json` 的 C04/C05/C07 完整 trace，均达到6次调用、最终 `limit_reached`；修复报告记录当时 `resolved_asset_id` 被统一清空的前置状态问题。
- **修改**：`facts.py` 保存来自用户消息的事实及来源；`graph.py/reconcile` 区分身份依赖与故障/停机依赖。可复用设备核实；确需重查时由图先执行并独立记录自动核实，之后再开放合法工具。模型提出的停机值不能覆盖用户事实。
- **结果**：固定用例及预期不变，单次修复后 C04/C05/C07 均完成，对应模型调用6→4、6→4、6→3；原12条共3次自动核实。相关24条事实/状态回归见 `tests/test_fact_reconciliation.py`，不调用真实模型API，需要模型响应时使用脚本替身。

### 2. 已知信息重复追问、混合工具批次与前置条件不足

- **问题**：已有故障摘要或停机信息时仍追问；同一响应混合查询与追问，产生拒绝和无效轮次。越权输入还需在守住审批的同时完成合法受理。
- **定位证据**：同一基线 C02/C11 首轮混合工具及后续多余追问。人工复核发现两次对已知事实的多余追问；旧版没有语义冗余标记，不能将缺失指标当0。
- **修改**：`llm.py` 使用经过真实 API 验证兼容的 `parallel_tool_calls=False`，依据状态重绑合法工具；`graph.py` 将 facts、missing_fields、核实状态提供给模型，保留逐call协议校验/拒绝；`required_question` 只问缺失或冲突字段。C11的优先级、班组、审批约束由确定性程序执行。
- **结果**：修复后 C02完成，C11进入正确的待确认草案，未被指令改成P0/越权班组或直接建单；原12条工具拒绝17→0、六轮耗尽3→0。不能据此称彻底解决提示词注入安全或所有重复问句。

### 3. “设备 ID＋名称/位置”组合输入被误报未知设备

- **问题**：有效ID附带名称时，旧查询把整个字符串当匹配词，混淆“设备不存在”和“设备存在但无规则”。
- **定位证据**：基线 C09 查询 `EQ-010 包装机` 被判 `unmatched_asset`；预期实际是设备存在、该故障类别无匹配规则。
- **修改**：`domain.py` 通用提取完整ID并精确查台账，附加名称/别名/位置用于一致性检查；多ID或冲突澄清，未知ID不模糊替换。图还核对完整用户身份线索，防止模型缩短查询掩盖冲突。24条设备查询单测见 `tests/test_asset_query.py`。
- **结果**：修复后 C09正确返回 `no_matching_rule`，不建单；这是正确拒绝/结束的业务通过，不是成功创建工单。不同组合表述另在新4条用例中验证，样本量仍小。

### 4. 主机真实调用通过、容器运行时却不能访问模型

- **问题**：构建/WSL探针成功不能证明 API 容器具有同样出网路径。
- **定位证据**：保留的 `reports/container_model_probe.json`、`container_network_diagnosis.json` 显示 DNS 成功，IPv4 TCP 超时、IPv6 errno101，容器没有运行时代理；核验原监听实际位于Windows。
- **修改**：项目网关限定中继、Compose运行时代理、内部服务NO_PROXY，保留现有卷及TLS校验。通用代码/模板可提交，主机代理值与凭证不进入项目。
- **结果**：最终镜像真实探针1次调用通过，中继连接计数1→2；内部API/UI检查均HTTP200且计数不增。再经实际HTTP验证正常确认、补充确认、取消3/3，10次模型调用、16.444秒，原2条任务的业务表与checkpoint原有行摘要不变。三个场景**没有包含真实重启测试**。

## E. 简历取舍建议与不可越过的事实边界

按智能体开发岗位相关度，优先从以下五项取三至五项，篇幅不足时删去环境细节；这些是项目成果候选，不自动证明本人能脱离辅助独立完成每一项：

1. **受约束的单Agent工具工作流**：Python/LangGraph，台账与规则查询、缺失追问、结构化草案；LLM语义分类与确定性业务校验分工，模拟10设备/3班组/6规则。
2. **人工确认与可恢复执行**：`interrupt`、SQLite checkpoint、当前草案版本绑定、唯一请求键；未批准/取消不建单、重复确认同一工单，恢复与故障窗口有明确回归证据。
3. **依据trace修复状态与工具协议**：字段依赖失效、合法工具限制、完整用户事实来源、精确设备组合查询；同模型/同六轮/同原判定下，固定12条由6/12变12/12，另4条单次通过。
4. **可运行接口与交互交付**：FastAPI + 纯HTTP Streamlit + Docker Compose命名卷本地部署；最终容器真实模型探针及3个真实HTTP场景验证。
5. **可追溯验证与诚实指标**：114条离线/替身测试，真实评测按时间戳保存成功和失败trace，模型请求/自动步骤分账；37→33请求、17→0拒绝，但耗时52.827→63.660秒，不宣称提速。

简历和面试中必须保留的边界：

- 全部业务数据模拟，没有接入真实企业资产台账、工单系统或设备，没有企业用户、上线业务收益和生产交付经历；目标用户只是演示角色。
- 单Agent业务受理与流转；不包装成多Agent协作系统、自主维修诊断、维修指导、真实设备控制、模型训练/微调或复杂RAG项目。开发时使用辅助工具/子任务协作不改变产品本身的单Agent架构。
- 云部署未验证；只验证本地WSL/Docker，不写云端上线或公网服务。当前代理方案依赖既有Windows代理与运行中的WSL中继，不是通用云网络方案。
- 无生产鉴权；草案摘要用于版本绑定，不是认证或签名。SQLite两库、单worker、进程内锁加本地文件锁是演示规模方案，未验证生产级高并发、多副本或分布式事务。
- 启发式事实提取可能在复杂否定、时间关系、指代和罕见设备名称中漏提/误判；故障语义类别仍受模型影响，规则校验与人工确认不等于维修安全认证。
- 12+4都是有限样本单次运行；不是稳定泛化率100%，114条测试不能全部称真实LLM评测。模型请求减少没有证实更低成本或更快响应。
- 个人真实参与、独立操作与掌握程度需本人确认。用户下一步将亲自操作演示、读代码；本文不能先行将这些后续计划写成已完成的个人经历。
